# Автотести фільтра «Ціна» на makeup.com.ua

Тестове завдання QA Automation: Playwright + TypeScript.
Тести покривають фільтр **«Вартість»** (фільтр ціни) на сторінці категорії
[makeup.com.ua/ua/categorys/3/](https://makeup.com.ua/ua/categorys/3/) у **десктопній** і **мобільній** версіях.

## Швидкий старт

Потрібен Node.js 20 або новіший.

```bash
npm ci                     # залежності
npx playwright install chromium   # браузер (у CI: npm run install:browsers, з системними пакетами)

npm test                   # усі тести: unit + desktop + mobile
```

| Команда | Що робить |
|---|---|
| `npm test` | Усі проєкти: `unit`, `desktop-chrome`, `mobile-chrome` |
| `npm run test:desktop` | Лише десктоп (Chrome, 1440×900) |
| `npm run test:mobile` | Лише мобільна версія (Pixel 7: touch, mobile UA, viewport) |
| `npm run test:unit` | Unit-тести утиліт (без браузера, менше секунди) |
| `npm run test:headed` | З видимим браузером, в один потік (зручно для дебагу) |
| `npm run test:strict` | Строгий режим: будь-який товар поза діапазоном валить тест (див. [дефекти](#знайдені-дефекти)) |
| `npm run report` | Відкрити HTML-звіт останнього прогону |
| `npm run typecheck` | Перевірка типів TypeScript |

Окремий тест: `npx playwright test -g "посилання з фільтром"`, окремий файл: `npx playwright test tests/e2e/price-filter.state.spec.ts`.

### Налаштування (змінні середовища, усі необов'язкові)

| Змінна | За замовчуванням | Опис |
|---|---|---|
| `BASE_URL` | `https://makeup.com.ua` | Середовище (prod/stage) |
| `CATEGORY_PATH` | `/ua/categorys/3/` | Будь-яка інша категорія з фільтром «Вартість» (формат `/ua/categorys/<id>/`) |
| `WORKERS` | `2` | Кількість паралельних воркерів (див. [стабільність](#стабільність)) |
| `PRICE_MISMATCH_TOLERANCE` | `0.05` | Допустима частка товарів, у яких дефект даних |
| `STRICT_PRICE_CHECK` | `0` | `1`: допуск 0 |

Приклад: `CATEGORY_PATH=/ua/categorys/<id>/ npm run test:mobile`. Шаблон лежить у `.env.example`.

## Структура проєкту

```
├── playwright.config.ts            # проєкти unit / desktop-chrome / mobile-chrome, ретраї, трейси
├── src/
│   ├── config/env.ts               # конфігурація з env із безпечними дефолтами
│   ├── fixtures/index.ts           # test.extend: підготовка контексту, categoryPage, catalogApi
│   ├── pages/category-page.ts      # Page Object сторінки категорії: open, apply*, reload, loadMore
│   ├── components/
│   │   ├── price-filter.ts         # фільтр «Вартість»; тут уся різниця між desktop і mobile
│   │   ├── product-grid.ts         # сітка товарів, лічильник, синхронізація з відповіддю API
│   │   └── selectors.ts            # усі селектори в одному місці
│   ├── api/catalog-api.ts          # типи й предикати API каталогу, деталі товару з варіантами
│   ├── assertions/                 # доменні перевірки: «фільтр застосовано», «ціни в діапазоні»
│   └── utils/price.ts              # чисті функції: парсинг цін і пресетів, діапазони, перцентилі
├── tests/
│   ├── e2e/                        # ОДНІ Й ТІ САМІ специ для desktop і mobile
│   │   ├── price-filter.presets.spec.ts
│   │   ├── price-filter.manual-input.spec.ts
│   │   ├── price-filter.state.spec.ts
│   │   └── price-filter.known-issues.spec.ts
│   └── unit/price.spec.ts
└── .github/workflows/playwright.yml   # CI: матриця desktop/mobile, HTML-звіт як артефакт, нічний прогін
```

Шари: **тест → Page Object / компоненти → селектори та API-хелпери → утиліти**. Тест описує сценарій мовою
предметної області (`choosePreset`, `setPriceRange`, `expectPriceFilterApplied`) і не знає ні про CSS,
ні про те, що на мобільному фільтр сховано в шторці.

## Що покрито

Усі e2e-тести запускаються в обох проєктах: `desktop-chrome` і `mobile-chrome`.

| Сценарій | Файл |
|---|---|
| Пресети відображаються, діапазони впорядковані й стикуються без «дір» | presets |
| Пресет «Менше N», «N – M» і «Більше N» фільтрують видачу | presets |
| Застосування кожного пресету; сума видач покриває каталог | presets |
| Ручний діапазон «Від – До» | manual-input |
| Лише «Від»; лише «До» | manual-input |
| Межі включні: «Від» = «До» = ціна наявного товару | manual-input |
| Діапазон без товарів дає порожню видачу й «0 товарів» | manual-input |
| Поля приймають лише цифри | manual-input |
| Deep link: URL з `#price_from=…&price_to=…` відкриває відфільтровану видачу | state |
| Фільтр зберігається після перезавантаження | state |
| «Показати ще» довантажує наступну сторінку з тим самим фільтром | state |
| Скидання через тег фільтра | state |
| Desktop: «Зняти фільтри» | state |
| Mobile: «Очистити» у шторці; «Застосувати» закриває шторку | state |
| «Від» > «До» (відомий дефект, `test.fixme`) | known-issues |

**Що перевіряється після кожного застосування фільтра** (`expectPriceFilterApplied`):

1. Фронтенд надіслав запит з **точними** `priceFrom` / `priceTo` (контракт UI → API).
2. Стан збережено в hash URL, полях «Від» / «До» і в тегу «від X до Y».
3. Лічильник «N товарів» дорівнює `availableCount` з відповіді, і він не більший за кількість товарів без фільтра.
4. Сітка відображає саме цю відповідь: ті самі товари в тому ж порядку, з тими ж цінами.
5. Ціна кожного товару в наявності потрапляє в діапазон (з урахуванням варіантів, див. нижче).

## Як тести не залежать від конкретних товарів і цін

- **Пресети зчитуються з UI** під час прогону й розбираються з підписів («Менше 50 ₴», «50 ₴ - 100 ₴», «Більше 5000 ₴»).
  Якщо магазин змінить діапазони, тести не зламаються. Для сценаріїв пресет обирається за формою діапазону, а не за позицією.
- **Ручні діапазони рахуються з живих даних**: перцентилі (p25 / p50 / p75) цін на сторінці без фільтра.
  Так видача завжди непорожня. Для перевірки включних меж береться ціна, яка точно є в каталозі зараз.
- **Джерело правди — відповідь API**, яку отримав сам фронтенд (`waitForResponse`), а не захардкоджені очікування.
- **Бізнес-правило варіантів.** Фільтр знаходить товар, якщо в діапазон потрапляє ціна будь-якого його варіанта
  (об'єм або склад), а картка показує ціну варіанта за замовчуванням. Тому для картки з ціною «поза діапазоном»
  тест бере варіанти з `/shop/v1/products/{id}/` і зараховує товар, якщо хоча б один варіант у діапазоні.
- Відсутні товари (без ціни, «Немає в наявності») не враховуються в перевірці цін, але перевіряється, що в API вони справді `inStock: false`.

## Стабільність

| Проблема | Рішення |
|---|---|
| Сторінка рендериться на сервері, а React гідратується через ~3–4 с. Кліки до цього ігноруються, а введене стирається | Чекаємо ознаку гідратації на полі фільтра (`__reactProps`). Дія з фільтром повторюється через `toPass`, доки не піде очікуваний запит |
| При першому вході AWS WAF робить challenge і перезавантажує сторінку | `expect.poll` замість одноразового `waitForFunction`, яке падає на навігації |
| Поля застосовуються на `blur`. Якщо одразу ввести друге поле, перерендер після першого його стирає | `setPriceRange` комітить кожне поле окремо і чекає на відповідь |
| На сторінці є блоки інших категорій з тим самим ендпоінтом | Предикат відповіді звіряє ID категорії, `priceFrom`, `priceTo` і `offset` |
| Cookie-банер і підказка MAKEUP Rewards перекривають кнопки (особливо на mobile) | Стан «вже бачив» задається заздалегідь у фікстурі (cookie `accepted`, localStorage `global-store`). Сторінка не клікає по банерах |
| Каталог живий: кількість товарів «пливе» на кілька штук між запитами | Строго порівнюємо значення одного моменту (UI ↔ відповідь). Між різними моментами — з допуском ±1% |
| Продакшен троттлить паралельні прогони (`ERR_TIMED_OUT`, зависання API) | 2 воркери за замовчуванням, кеш деталей товару, ретраї API-запитів, блокування картинок |
| Жодних `sleep` | Синхронізуємося на подіях: відповідь API, ID карток у DOM, видимість елементів |
| Селектори | Лише стабільна BEM-частина класів CSS-модулів (`.PriceSelector__input`), без хешів збірки. Ролі й тексти там, де вони є |

Сторонні скрипти (GTM тощо) **навмисно не блокуються**: без них фронтенд сайту не ініціалізує фільтр
(перевірено: блокування ламає застосування фільтра).

Діагностика падінь: trace, скриншот і відео зберігаються для кожного падіння (`npm run report`).
Звіт кожної перевірки цін додається до тесту як JSON-attachment.

## Знайдені дефекти

Під час розробки знайдено такі проблеми. Тести їх **фіксують**, а не ховають.

1. **Товари поза діапазоном у видачі.** Приблизно 1 товар на 100: жоден варіант товару не потрапляє в діапазон фільтра.
   Ймовірно, ціновий індекс пошуку застарів відносно поточних цін. Приклади на момент написання:
   - «500 ₴ – 750 ₴»: Banderas King of Seduction, картка 849 ₴, варіанти 803–1156 ₴;
   - «1000 ₴ – 5000 ₴»: Tiziana Terenzi Kirke, 10 473 ₴.

   Кожен такий товар потрапляє в annotation `data-defect` і в JSON-звіт тесту. Тест падає, якщо частка
   таких товарів перевищує `PRICE_MISMATCH_TOLERANCE` (5%). `npm run test:strict` вмикає нульовий допуск.
2. **«Від» > «До» без валідації.** Запит `priceFrom=900&priceTo=750` іде як є. Користувач бачить кілька
   товарів за ціною рівно «Від» і жодного повідомлення. Очікувано: межі міняються місцями або показується
   валідація. Тест є, але позначений `test.fixme` (прибрати `.fixme`, коли дефект виправлять).
3. **Недопустимий символ стирає вже введене число.** Посимвольний ввід `12a3` дає `3`, а `1-2` дає `2`.
   Тест перевіряє лише інваріант «у полі тільки цифри», а сама поведінка — UX-дефект.
4. **Відсутні товари з ціною 0 ₴ у видачі діапазонів** (наприклад, «100 ₴ – 250 ₴»). На UI вони показані
   як «Немає в наявності», тому це косметика API, а не порушення фільтра. Тести таких товарів не рахують.
5. Різниця між `total` і `availableCount` в API: без фільтра ціни `total` враховує відсутні товари, а з фільтром — ні.
   UI коректно показує `availableCount`. Окремого дефекту для користувача тут немає, але це варто знати при тестуванні API.

## Обмеження та що далі

- Тести працюють з продакшеном: дані змінюються, а WAF може обмежити трафік. Для регресу в CI краще stage з керованими даними.
- Сортування за ціною разом із фільтром і комбінації з іншими фільтрами (бренд, об'єм) — наступний логічний крок.
- Можна додати проєкт `mobile-safari` (WebKit, iPhone). Для цього достатньо ще одного запису в `projects` і `npx playwright install webkit`.
- Візуальні перевірки (скриншот-тести шторки й пресетів) свідомо не додавалися: контент банерів і товарів на проді нестабільний.
